# RAG Answering

## 目标

面对知识库问题时，你不能只做“检索一下然后回答”。

你需要完成完整闭环：

1. 判断问题需要什么检索结构
2. 执行检索计划
3. 对候选证据做验证和筛选
4. 输出带引用的最终答案

## 强制流程

### Step 1：先加载检索技能

先调用：

- `load_skill("rag-retrieval")`

目的是确认当前支持哪些检索模式、何时需要多步组合、何时必须回查原文验证。

### Step 2：使用 tool 层的检索计划模块

检索计划模块属于 Agent/tool 层能力，不属于 skill 本体。

执行时：

1. 如有需要，先调用 `get_retrieval_plan_schema()`
2. 根据你的判断组织 `plan_json`
3. 调用 `run_retrieval_plan(query, plan_json, group_id, doc_id)`

### Step 3：区分候选结果与已验证证据

你要区分：

- 结构化候选
  例如实体、关系候选
- 已验证的原文证据
  例如包含 `document_name`、`chunk_id`、`text` 的 chunk
- 不足或失败信息
  例如某个 step 没有召回、证据不足、验证失败

### Step 4：先证据摘要，再最终回答

最终回答时，必须先给出证据摘要，再给出结论。

## 证据原则

### 1. 优先已验证 chunk

如果某个结论只来自实体/关系召回，而没有原文支持，应明确说这是候选结论，尚未完成验证。

### 2. 不要把召回当事实

检索召回结果只是候选。
只有在问题匹配且证据充分时，才可以写入最终结论。

### 3. 支持复杂推理，但必须说明证据链

如果你做了多步推理，例如：

- 先找实体
- 再扩展关系
- 再回查原文
- 再做归纳总结

你需要让用户能看出结论是如何形成的。

## 推荐输出结构

### 证据摘要

- `[1] <document_name> / chunk_id=<...>：<关键证据摘录>`
- `[2] ...`

### 最终回答

- 基于证据给出自然语言答案
- 关键结论后标注引用，例如 `[1][3]`
- 如果某个结论只是推断而非直接证据，必须明确说明

## 何时必须补充检索

出现以下情况时，不要立刻结束：

- 只有结构化候选，没有原文证据
- 检索结果和问题不完全匹配
- 证据之间冲突
- 结果太少，不足以支持结论

这时应增加验证或补充 step，再次调用检索计划模块。
